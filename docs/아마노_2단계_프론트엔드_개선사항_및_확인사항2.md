# 아마노 2단계 구매 - 프론트엔드 개선사항 및 확인사항

> 본 문서는 아마노 2단계 구매 프로세스 연동 후, 프론트엔드 개선 권고사항과 **백엔드/외부 확인이 필요한 사항**을 정리한 문서입니다.

## 개선사항 요약

| 번호 | 항목 | 처리 주체 | 우선순위 |
|------|------|----------|----------|
| 1 | gdsTrdId 버그 수정 | 프론트 | 높음 |

## 1. gdsTrdId 버그 수정 (프론트)

### 문제

`setAmanoGdsTrdId(gdsTrdId)` 호출 직후, 같은 실행 흐름에서 `body`를 만들 때 `amanoGdsTrdId`를 사용하고 있음. React `setState`는 비동기이므로 이 시점에는 아직 이전 값(빈 문자열)이 남아있을 수 있음.

```javascript
// pending 성공 시
setAmanoGdsTrdId(gdsTrdId);  // 비동기 업데이트
// ...
const body = {
  ...(amanoGdsTrdId && {moid: amanoGdsTrdId}),  // ❌ 여전히 빈 문자열일 수 있음
};
```

### 수정 권장

pending 응답에서 받은 `gdsTrdId`를 **지역 변수**에 저장하고, 그 값을 body에 바로 사용.

```javascript
let pendingGdsTrdId = '';
// pending 성공 시
pendingGdsTrdId = json?.data?.gdsTrdId || '';
setAmanoGdsTrdId(pendingGdsTrdId);
// ...
const body = { ...(pendingGdsTrdId && {moid: pendingGdsTrdId}) };
```

## 2. BASE_URL 상수 사용 (프론트)

### 현황

`http://cafe.wisemobile.kr:8080/api/amano`가 `reservation-check.tsx`, `reservation-simple-pay.tsx`, `reservation-detail.tsx` 등에 하드코딩되어 있음.

### 수정 권장

`~constants/constant`의 `BASE_URL`을 사용.

```javascript
import { BASE_URL } from '~constants/constant';
const AMANO_BASE = `${BASE_URL.replace(/\/$/, '')}/api/amano`;
```

서버 주소 변경 시 한 곳만 수정하면 됨.

## 4. 주차권 pending body의 plotId 포함 여부 (**백엔드 확인 필요**)

### 확인 대상

백엔드 / API 스펙

### 현황

- **가이드 예시**: 주차권 pending body에는 `plotId`가 없음 (`gdsId`, `pinResveDtm`, `carNo`, `purchaseDate`만 있음)
- **현재 프론트**: 주차권 pending 요청에 `plotId`를 포함해서 전송 중

### 확인 요청 문구

> "주차권 pending API 요청에 `plotId`를 포함해도 되나요, 아니면 제거해야 하나요?"

### ✅ 백엔드 확인 결과 (2025-01-30)

- 백엔드 요청 DTO(`ParkingTicketPendingRequest`)에는 **plotId 필드 없음**. (아마노 API 3.5.1 스펙 반영)
- 프론트에서 `plotId`를 보내도 **추가 필드는 무시**되므로 에러는 나지 않음.
- **권장:** 스펙과 맞추기 위해 **제거해도 됨**. 유지해도 동작에는 문제 없음.

## 5. 정기권 pending 응답 구조 (**백엔드 확인 필요**)

### 확인 대상

실제 API 응답 / 백엔드

### 현황

- **가이드**: `data.seasonGoodsStatus` 배열에 건별 결과가 있고, 각 항목에 `gdsTrdId`, `status` 등 포함
- **현재 프론트**: `json?.data?.gdsTrdId` 하나만 사용 중

### 확인 요청 문구

> "정기권 1건 구매 시 응답에서 `gdsTrdId`는 어디에 옵니까?  
> `data.gdsTrdId` 인가요, 아니면 `data.seasonGoodsStatus[0].gdsTrdId` 인가요?"

### ✅ 백엔드 확인 결과 (2025-01-30)

- 백엔드 응답 DTO(`SeasonalPassPendingResponse`) 구조: **`data.plotId`**, **`data.seasonGoodsStatus`**(배열) 만 존재. **`data.gdsTrdId`는 없음.**
- 정기권 1건이어도 `gdsTrdId`는 **`data.seasonGoodsStatus[0].gdsTrdId`** 에 있음.
- **프론트 수정 필요:** `json?.data?.gdsTrdId` → **`json?.data?.seasonGoodsStatus?.[0]?.gdsTrdId`** (1건 기준). 여러 건이면 `seasonGoodsStatus` 배열을 순회하며 `status === 'REGI'` 인 건의 `gdsTrdId` 수집.

## 6. Complete API 호출 시점 (**백엔드/PHP 확인 필요**)

### 확인 대상

PHP / 백엔드 담당자

### 현황

- **현재**: WebView `onLoadEnd` 시점에 complete API 호출
- **가정**: WebView 로드 완료 = 결제 성공

### 확인 요청 문구

> "`android_payResult_ticket.php`가 로드된다는 것이 결제 성공을 의미하나요?  
> 아니면 실패 시에도 이 페이지가 로드되나요?  
> complete API는 프론트에서 호출해야 하나요, 아니면 백엔드에서 호출하나요?"

### ✅ 백엔드 확인 결과 (2025-01-30)

- **Complete API 호출 주체:** 가이드대로 **프론트에서** 결제가 성공했다고 판단되는 시점에 `complete` API를 호출하는 방식이 맞음. (백엔드에서 자동 호출하는 구조 아님)
- **호출 시점:** “결제가 최종 성공했다”고 확정되는 시점(예: NicePay 승인 결과 수신 후, 또는 해당 PHP가 “결제 성공”일 때만 로드된다는 전제 하에 그 페이지 로드 시)에 프론트에서 한 번 호출하면 됨.
- **PHP 페이지 의미:** `android_payResult_ticket.php`가 **성공 시에만** 로드되는지, **실패 시에도** 로드되는지는 결제(NicePay 등) 연동 담당 또는 PHP 쪽 확인 필요. 실패 시에도 같은 URL이 열리면, 그때는 complete를 호출하지 않도록 프론트에서 성공/실패 구분 로직 필요.
